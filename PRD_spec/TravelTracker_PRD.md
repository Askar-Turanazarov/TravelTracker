# Product Requirements Document (PRD) — TravelTracker

**Продукт:** TravelTracker (Интерактивный трекер путешествий и карта посещенных мест)  
**Версия:** 1.0.0  
**Автор:** CPTO / Product Lead  
**Статус:** Approved for Development  
**Целевой Time-to-Market (TTM):** 5 рабочих дней (MVP)  

---

## 1. Executive Summary

### 1.1. Суть продукта
**TravelTracker** — это лаконичный веб-сервис для визуализации и учета личных путешествий. Приложение позволяет пользователю фиксировать посещенные города и страны, выставлять личные оценки, сохранять заметки и анализировать географический охват своего опыта через интерактивную карту с темной эстетической темой и мгновенную статистику (% посещенного мира, количество стран и городов).

### 1.2. Бизнес-цели и Ценность (ROI)
* **Цель:** Создать высокоэффектное, визуально безупречное full-stack приложение в рамках учебного проекта с минимальными затратами на разработку и нулевыми рисками превышения сроков.
* **Бизнес-ценность (ROI):** Максимальное соотношение «Затраченные усилия / Эффектность на демонстрации (ВАУ-фактор)». Продукт демонстрирует умение работать со стандартизованными данными (ISO-коды), геопространственной визуализацией (Leaflet.js) и агрегированной аналитикой.

### 1.3. График реализации (Roadmap MVP)
* **Дни 1–2:** Проектирование БД, установка API контрактов, настройка OpenCode backend (CRUD).
* **Дни 3–4:** Разработка UI в Gemini CLI (React + Tailwind + Leaflet.js), интеграция с API.
* **День 5:** Тестирование edge-cases, полировка визуальных эффектов (dark theme, emoji-flags) и финальный релиз.

## 2. Target Audience & User Roles

### 2.1. Целевая аудитория (User Personas)
1. **Любитель путешествий (Casual Traveler):** Хочет красиво оформить свои прошлые поездки, вести личную карту и видеть прогресс освоения планеты.
2. **Цифровой кочевник (Digital Nomad):** Фиксирует частые смены локаций, оценивает места для повторного визита.
3. **Презентер / Ревьюер кода (Portfolio Evaluator):** Оценивает скорость работы интерфейса, чистоту архитектуры, обработку крайних случаев и эстетику UI.

### 2.2. Ролевая модель
* **Guest (Гость):** Имеет доступ в режиме просмотрщика (демо-данные без права сохранения в бэкенд).
* **Traveler (Авторизованный пользователь):** Полный владелец своего профиля (Full CRUD по своим локациям, просмотр персональной аналитики).

## 3. Functional Requirements (Функциональные требования)

### FR-1: Дашборд и Главный экран
* **FR-1.1:** Отображение плашки метрик в верхней части экрана:
  * Общее количество посещенных уникальных стран.
  * Процент посещенного мира (расчет от 195 стран, признанных ООН).
  * Общее количество посещенных городов.
* **FR-1.2:** Фильтрация и поиск по списку поездок (по названию страны, города или рейтингу).

### FR-2: Интерактивная Карта (Leaflet.js Visualizer)
* **FR-2.1:** Полноразмерная интерактивная карта с темным стилем подложки (CartoDB Dark Matter / Mapbox Dark).
* **FR-2.2:** Автоматическая установка интерактивных пинов (маркеров) по координатам (`lat`, `lng`) каждого посещенного города.
* **FR-2.3:** Клик по маркеру открывает карточку-попап с краткой информацией: Флаг страны, Название города, Дата визита, Оценка (звезды 1–5).

### FR-3: Управление записями (CRUD Поездок)
* **FR-3.1:** Добавление новой поездки с обязательной валидацией полей:
  * Страна (выбор из выпадающего списка с автозаполнением, сохраняется в ISO 3166-1 alpha-2, например `IT`, `JP`).
  * Город (текстовое поле).
  * Дата посещения (`YYYY-MM-DD`).
  * Оценка (от 1 до 5 звезд).
  * Заметка / Впечатления (текст до 1000 символов, опционально).
  * Координаты `lat`/`lng` (автоматическое определение или ручной ввод).
* **FR-3.2:** Редактирование существующей поездки.
* **FR-3.3:** Удаление поездки с модальным подтверждением действия.

### FR-4: Стандартизация данных и Флаги
* **FR-4.1:** Все страны жестко привязываются к двухсимвольным ISO-кодам (`country_code`).
* **FR-4.2:** Отображение флагов стран на клиенте выполняется через эмодзи (`ISO alpha-2 -> Emoji Unicode`) или векторные SVG-иконки без загрузки сторонних тяжелых растровых изображений.

## 4. Acceptance Criteria (Критерии приемки — Given-When-Then)

### AC-1: Расчет процента посещенных стран (FR-1)
* **Given:** Пользователь имеет 12 уникальных посещенных стран в базе данных.
* **When:** Пользователь открывает дашборд.
* **Then:** Плашка метрики «Посещено стран» отображает `12`, а «Прогресс мира» отображает `6.15%` ($12 / 195 	imes 100$, округленное до 2 знаков).

### AC-2: Добавление новой локации (FR-3)
* **Given:** Пользователь находится на форме «Добавить поездку».
* **When:** Пользователь выбирает страну «Япония» (`JP`), вводит город «Токио», дату `2026-04-12`, ставит оценку `5` и нажимает «Сохранить».
* **Then:** Запись отправляется на бэкенд, возвращает статус `201 Created`, карта мгновенно добавляет пин Токио ($35.6762, 139.6503$), а счетчик уникальных стран увеличивается на 1 (если Япония не была посещена ранее).

### AC-3: Валидация ISO-кода (FR-4)
* **Given:** Бэкенд получает POST-запрос на создание поездки.
* **When:** Поле `country_code` содержит недопустимое значение (например, `JPN` вместо `JP` или пустую строку).
* **Then:** Сервер возвращает ошибку `400 Bad Request` с сообщением `"Invalid ISO 3166-1 alpha-2 country code"`.

### AC-4: Отображение карточки при клике на маркер карты (FR-2)
* **Given:** Карта содержит маркер для города «Рим».
* **When:** Пользователь кликает по маркеру «Рим».
* **Then:** В центре экрана всплывает попап с флагом 🇮🇹, названием «Рим, Италия», датой визита и рейтингом ⭐⭐⭐⭐⭐.

## 5. Non-Functional Requirements (NFR — Нефункциональные требования)

### 5.1. Производительность (Performance)
* **Latency API:** Ответы бэкенда на CRUD-запросы не должны превышать $p_{99} < 150	ext{ms}$.
* **Время рендеринга карты:** Первичный рендеринг карты с 50 пинами не должен превышать $500	ext{ms}$.
* **Размер бандла:** Общий бандл фронтенда (Gzip) $< 350	ext{KB}$ (без учета тайлов карты, подгружаемых по требованию).

### 5.2. Безопасность (Security)
* **Sanitization:** Все текстовые заметки пользователя обязаны проходишь через XSS-санитизацию на сервере перед сохранением.
* **CORS:** Разрешены запросы только с доверенного доменного имени клиентского приложения.

### 5.3. Надежность и Доступность (SLA)
* **SLA Uptime:** 99.9% доступности сервиса.
* **Graceful Degradation:** При недоступности подложки карты (тайлов CartoDB) приложение отображает сообщение об ошибке тайлов, сохраняя доступ к табличному списку и статистике.

### 5.4. Стандарты и Совместимость
* **Совместимость с устройствами:** Корректное отображение на Desktop (1920x1080), Laptop (1366x768) и Mobile (375x812).
* **Стандарты кодирования коорднат:** Формат `WGS 84` (широта/долгота в десятичных градусах Float).

## 6. Key Performance Indicators (KPIs)

### 6.1. Продуктовые и Пользовательские метрики
* **Average Time to Add Trip:** Время заполнения формы создания поездки $< 15$ секунд.
* **User Engagement:** Среднее количество сохраненных поездок на активного пользователя $\ge 5$.

### 6.2. Технические и Инженерные метрики
* **Zero Layout Shift (CLS):** Коэффициент сдвига макета при загрузке карты $CLS < 0.1$.
* **Crash Rate:** Процент сессий с необработанными фронтенд-ошибками $< 0.1\%$.
* **Code Coverage:** Покрытие бэкенд-логики юнит-тестами $\ge 80\%$.

## 8. Data Architecture Overview (Краткая структура)

Единый источник правды для поездки должен содержать следующие поля:
* `id` (UUID, Primary Key)
* `user_id` (UUID, Foreign Key)
* `city_name` (String, Not Null)
* `country_name` (String, Not Null)
* `country_code` (String, ISO 2 chars, Not Null, Index)
* `visited_at` (Date, Not Null)
* `rating` (Integer, 1-5, Not Null)
* `lat` (Decimal/Float, Not Null)
* `lng` (Decimal/Float, Not Null)
* `notes` (Text, Nullable)
* `created_at` (Timestamp)
