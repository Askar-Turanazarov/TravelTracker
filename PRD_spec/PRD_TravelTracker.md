## 1. Executive Summary

### 1.1 Суть продукта
TravelMap — минималистичное веб-приложение для приватного визуального учёта посещённых стран и городов. Пользователь добавляет геолокации из закрытого справочника (ISO 3166-1 alpha-2 + внутренняя база центроидов городов), система рендерит интерактивную тёмную карту (Leaflet.js + CartoDB Dark Matter) с маркерами и агрегированную инфографику («освоено N% мира», количество стран/городов, хронология).

Продукт сознательно отказывается от функций конкурентов (планирование маршрутов, бронирование, соцсеть с лентой чужого контента) в пользу единственного УТП: **красивая, быстрая, приватная личная карта мира**.

### 1.2 Бизнес-цели
| Цель | Описание |
|---|---|
| Портфолио-эффект | Демонстрация зрелой инженерной экспертизы: геопространственные данные, SQL-агрегации, RBAC, реактивный UI |
| Личный бренд | Проект — витрина навыков full-stack разработки для IT-ревьюеров и нанимающих менеджеров |
| Монетизация | Отсутствует в рамках MVP (см. п.6.3 — потенциал масштабирования вне скоупа) |

### 1.3 Финансовая обоснованность (ROI/Value)
- **Бюджет разработки:** $0 (только open-source: React, Tailwind, Leaflet.js, PostgreSQL, бесплатные тайлы CartoDB).
- **Стоимость владения (инфраструктура):** минимальна — statless REST API + PostgreSQL, без тяжёлых медиафайлов (фото исключены из MVP), что снижает требования к storage и CDN до нуля.
- **Возврат инвестиций:** нефинансовый — измеряется качеством портфолио (см. KPI, п.5) и потенциальной конверсией в оффер/фриланс-заказы.
- **Риск финансовых потерь:** отсутствует — нет платных API (Google Maps исключён намеренно), нет платных тайлов, нет облачных сервисов с оплатой за трафик медиа.

### 1.4 Time-to-Market
Жёсткий сжатый срок запуска MVP. Разработка ведётся в 3 параллелизуемых потока (Backend-first рекомендуется, см. п.6.2 Roadmap), без буфера на созвоны — документ закрывает все уточняющие вопросы заранее.

## 2. Target Audience & User Roles

### 2.1 Целевая аудитория

| Сегмент | Потребность | Ключевой сценарий использования |
|---|---|---|
| **Casual Traveler** | Красивый визуальный дневник, шаринг скриншотов | Заходит 2-4 раза в год, добавляет 1-3 локации за раз, делает скриншот карты |
| **Digital Nomad** | Точный хронологический учёт с датами и заметками | Частые заходы, ввод дат приезда/отъезда, личные заметки к каждой локации |
| **IT-ревьюер / HR** | Оценка архитектуры, UX, качества кода | Разовое посещение, тестирует CRUD, скорость карты, эстетику дашборда |

### 2.2 Ролевая модель (RBAC)

| Роль | Права доступа |
|---|---|
| **Guest** | Просмотр только публичного лендинга. Нет доступа к API данных пользователей. |
| **Traveler** (авторизован, JWT) | Полный CRUD исключительно над собственными гео-метками (`user_id` = owner). Доступ к личному дашборду и статистике. |
| **Admin** | Полный доступ на чтение ко всем записям всех пользователей (модерация, аналитика). Доступ к админ-эндпоинтам без права редактирования чужих меток (см. NFR 4.3 — принцип наименьших привилегий). |

### 2.3 User Stories (ключевые)

- **US-01:** Как Traveler, я хочу добавить страну из выпадающего списка (ISO 3166-1 alpha-2), чтобы она появилась на моей карте с корректной геопривязкой.
- **US-02:** Как Traveler, я хочу выбрать город из справочника, привязанного к выбранной стране, чтобы избежать ошибок ввода и дублей.
- **US-03:** Как Traveler, я хочу видеть агрегированную статистику («X стран, Y городов, Z% мира освоено»), чтобы оценить прогресс.
- **US-04:** Как Traveler, я хочу добавить дату посещения и заметку к локации, чтобы вести хронологию поездок.
- **US-05:** Как Traveler, я хочу удалить или отредактировать ранее добавленную локацию.
- **US-06:** Как Guest, я хочу увидеть привлекательный лендинг с демо-картой, чтобы понять ценность продукта до регистрации.
- **US-07:** Как Admin, я хочу видеть список всех пользователей и агрегированную статистику по системе, чтобы модерировать контент.

## 3. Functional Requirements

### FR-01: Регистрация и аутентификация
**Описание:** Email + пароль, выдача JWT (access + refresh token).

**Acceptance Criteria:**
- **Given** пользователь вводит валидный email и пароль ≥8 символов, **When** отправляет форму регистрации, **Then** система создаёт запись в таблице `users`, хэширует пароль (bcrypt, cost factor ≥12), возвращает `201 Created` с access token (TTL 15 мин) и refresh token (TTL 7 дней).
- **Given** email уже зарегистрирован, **When** пользователь пытается зарегистрироваться повторно, **Then** система возвращает `409 Conflict` с телом `{"error": "EMAIL_ALREADY_EXISTS"}`.
- **Given** валидные credentials, **When** пользователь логинится, **Then** система возвращает `200 OK` с новой парой токенов.
- **Given** невалидный пароль, **When** пользователь логинится, **Then** система возвращает `401 Unauthorized` без раскрытия, существует ли email (защита от enumeration).

### FR-02: Добавление гео-метки (страна)
**Описание:** Traveler выбирает страну строго из справочника ISO 3166-1 alpha-2 (dropdown с поиском, не free-text).

**Acceptance Criteria:**
- **Given** авторизованный Traveler, **When** он выбирает страну из справочника и подтверждает, **Then** создаётся запись в `visited_countries` со связкой `user_id` + `country_code`, возвращается `201 Created`.
- **Given** страна уже добавлена этим пользователем, **When** он пытается добавить её повторно, **Then** система возвращает `409 Conflict` (уникальный constraint `UNIQUE(user_id, country_code)`).
- **Given** попытка передать произвольную текстовую строку вместо кода из справочника, **When** запрос валидируется, **Then** система возвращает `422 Unprocessable Entity` (жёсткая enum-валидация на backend, не только на UI).

### FR-03: Добавление гео-метки (город)
**Описание:** Город выбирается из внутреннего справочника центроидов, привязанного к ранее выбранной стране.

**Acceptance Criteria:**
- **Given** страна уже добавлена в профиль пользователя, **When** Traveler открывает форму добавления города, **Then** dropdown городов фильтруется только по `country_code` выбранной страны.
- **Given** выбран город, дата посещения (опционально) и заметка (опционально, ≤500 символов), **When** форма отправлена, **Then** создаётся запись в `visited_cities` со ссылкой на `city_id` из справочника, `visit_date`, `note`.
- **Given** попытка добавить город без предварительно добавленной страны, **When** запрос отправлен, **Then** система возвращает `400 Bad Request` (`{"error": "COUNTRY_NOT_ADDED"}`).

### FR-04: Интерактивная карта
**Описание:** Leaflet.js рендерит тёмную карту (CartoDB Dark Matter tiles) с маркерами всех добавленных городов/стран пользователя.

**Acceptance Criteria:**
- **Given** у Traveler есть ≥1 добавленная локация, **When** открыт дашборд, **Then** карта отображает маркер для каждого города; страны без городов подсвечиваются заливкой полигона (GeoJSON слой).
- **Given** пользователь наводит/тапает на маркер, **When** взаимодействие происходит, **Then** появляется popup с названием города, датой визита и заметкой.
- **Given** данных нет (новый пользователь), **When** дашборд открыт, **Then** отображается пустое состояние (empty state) с призывом добавить первую локацию.

### FR-05: Дашборд статистики
**Описание:** Агрегированная инфографика: количество стран, городов, % «освоения мира».

**Acceptance Criteria:**
- **Given** у пользователя N уникальных стран, **When** дашборд загружен, **Then** отображается `N стран` и `N/195 × 100% мира` (195 — число стран-членов ООН, константа в конфиге).
- **Given** данные меняются (добавление/удаление), **When** мутация подтверждена, **Then** статистика на фронтенде обновляется реактивно без полной перезагрузки страницы (оптимистичный UI или инвалидация кэша запроса).
- Расчёт агрегатов выполняется на уровне SQL (`COUNT DISTINCT`), не в коде приложения, во избежание рассинхрона при масштабировании (см. SPEC п.2).

### FR-06: Редактирование и удаление локаций
**Acceptance Criteria:**
- **Given** запись принадлежит текущему пользователю (`user_id` совпадает с owner), **When** отправлен `PATCH`/`DELETE`, **Then** операция выполняется и возвращается `200 OK`.
- **Given** запись принадлежит другому пользователю, **When** Traveler пытается её изменить, **Then** система возвращает `403 Forbidden` (проверка на уровне бэкенда, не только скрытие в UI).
- **Given** удаление страны, у которой есть привязанные города, **When** запрос удаления страны отправлен, **Then** система удаляет каскадно связанные города (`ON DELETE CASCADE`) с явным предупреждением в UI перед подтверждением.

### FR-07: Публичный лендинг
**Acceptance Criteria:**
- **Given** неавторизованный Guest, **When** открывает корневой URL, **Then** видит статичный лендинг с демо-картой (моковые данные, без реального API-запроса к БД) и CTA на регистрацию.

### FR-08: Admin-панель (базовая)
**Acceptance Criteria:**
- **Given** пользователь с ролью `admin`, **When** обращается к `/api/admin/users`, **Then** получает список всех пользователей с их агрегатами (кол-во стран/городов), только на чтение.
- **Given** пользователь с ролью `traveler` пытается обратиться к admin-эндпоинту, **When** запрос отправлен, **Then** возвращается `403 Forbidden`.

## 4. Non-Functional Requirements (NFR)

### 4.1 Производительность
- Время отклика API для CRUD-операций над локациями: **< 150 мс** при p95, при нагрузке до 100 RPS (соответствует профилю портфолио-проекта, не enterprise).
- Первичная загрузка карты (Time to Interactive для Leaflet-компонента): **< 1.5 сек** на 3G Fast throttling.
- SQL-агрегация статистики (`COUNT DISTINCT` по странам/городам) должна выполняться **< 50 мс** при объёме до 10,000 записей на пользователя (индексы на `user_id`).

### 4.2 Безопасность
- Пароли хранятся только в виде bcrypt-хэша (cost ≥12), plaintext никогда не логируется.
- JWT access token TTL 15 минут, refresh token TTL 7 дней, ротация refresh token при каждом использовании (refresh token rotation).
- Все мутирующие эндпоинты (`POST`/`PATCH`/`DELETE`) проверяют владение ресурсом на уровне бэкенда (запрет IDOR — Insecure Direct Object Reference).
- Rate limiting на `/auth/login`: **5 попыток / 15 минут / IP**, во избежание brute-force.
- CORS настроен строго на whitelist доменов фронтенда, без wildcard `*` в production.

### 4.3 Отказоустойчивость и целостность данных
- Уникальный constraint `UNIQUE(user_id, country_code)` и `UNIQUE(user_id, city_id)` на уровне БД — защита от дублей независимо от фронтенд-валидации.
- Foreign key constraints между `visited_cities.country_code` и `countries_reference.code` — гарантия, что нельзя добавить город без валидной страны-родителя.
- Backend является единственным источником истины для enum-валидации (ISO-кодов) — frontend-валидация дублирующая, не единственная.

### 4.4 Соответствие стандартам
- GDPR: право пользователя на полное удаление аккаунта и всех связанных данных (`DELETE /api/users/me` → каскадное удаление, hard delete, не soft delete).
- Персональные данные (email, заметки) не передаются третьим лицам; отсутствие сторонней аналитики/трекеров в MVP.
- PCI-DSS: не применимо (отсутствует обработка платежей в MVP).

### 4.5 Ограничения инфраструктуры (заданные)
- Запрещена загрузка медиафайлов (фото) — экономия storage/bandwidth.
- Запрещено использование платных гео-API (Google Maps и аналоги) — используется только внутренний справочник центроидов + бесплатные тайлы CartoDB Dark Matter.
- Все справочники (страны, города) — статичные seed-данные в PostgreSQL, не внешние API-вызовы в рантайме.

## 5. Key Performance Indicators (KPIs)

### 5.1 Продуктовые метрики (для портфолио-демонстрации)
| Метрика | Целевое значение |
|---|---|
| Time to First Marker (от регистрации до первой добавленной локации) | < 60 секунд в демо-сценарии |
| Lighthouse Performance Score (фронтенд) | ≥ 90 |
| Lighthouse Accessibility Score | ≥ 90 |
| Успешность CRUD-операций без ошибок (QA smoke-тест) | 100% на happy path |

### 5.2 Инженерные метрики
| Метрика | Целевое значение |
|---|---|
| API test coverage (unit + integration) | ≥ 70% на критичных модулях (auth, CRUD локаций) |
| p95 latency CRUD-эндпоинтов | < 150 мс |
| Количество критичных багов на релизе | 0 |

### 5.3 Метрики «портфолио-эффекта» (нефинансовый ROI)
- Наличие в публичном GitHub с чистой историей коммитов и README.
- Задокументированная архитектура (ER-диаграмма БД, API-контракты) — см. SPEC.
- Отсутствие security-антипаттернов при код-ревью (IDOR, SQL-инъекции, plaintext-пароли).

## 6. Project Risks & Roadmap

### 6.1 Анализ рисков

| Риск | Тип | Вероятность | Митигация |
|---|---|---|---|
| Некорректные/неполные данные о центроидах городов во внутреннем справочнике | Технический | Средняя | Использовать проверенный открытый датасет (напр. GeoNames city subset) как основу seed-данных, ограничить MVP крупными городами (population > 100k) |
| Превышение сроков из-за одновременной разработки Frontend+Backend | Операционный | Высокая | Строгий backend-first подход (см. Roadmap 6.2) — фронтенд получает готовый API-контракт и мокирует данные параллельно |
| Разрастание скоупа (feature creep: фото, соцфункции) | Продуктовый | Средняя | Жёсткая фиксация MVP-скоупа в этом PRD; всё вне списка FR-01…FR-08 — в Backlog v2 |
| Деградация производительности карты при большом числе маркеров | Технический | Низкая | Кластеризация маркеров (Leaflet.markercluster) закладывается в архитектуру заранее, даже если не активна в MVP |
| Бесплатные тайлы CartoDB имеют rate-limit/fair-use политику | Инфраструктурный | Низкая | Кэширование тайлов на уровне браузера (стандартное поведение Leaflet), мониторинг лимитов провайдера |

### 6.2 Roadmap (фазы запуска)

**Рекомендованная последовательность — Backend-first** (митигирует риск рассинхрона контрактов):

| Фаза | Содержание |
|---|---|
| **Фаза 1: Foundation** | Проектирование схемы БД, seed-справочников (страны/города), реализация auth (JWT), базовый CRUD API для локаций. Результат: рабочий API-контракт (см. SPEC) |
| **Фаза 2: Frontend Core** | Вёрстка на React + Tailwind, интеграция Leaflet.js + CartoDB Dark Matter, подключение к реальному API, формы добавления локаций с валидацией |
| **Фаза 3: Polish & Release** | Дашборд статистики (SQL-агрегации), пустые состояния, error handling, финальное QA, деплой |

### 6.3 Вне скоупа MVP (Backlog v2, не включать в текущую разработку)
- Загрузка фотографий к локациям.
- Социальные функции (публичные профили, лента, подписки).
- Монетизация (подписки, премиум-функции).
- Мобильное приложение (нативное) — MVP только responsive web.
- Экспорт карты в PDF/изображение.
